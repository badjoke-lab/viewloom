# ViewLoom Twitch Stream Map — City visualization / interaction specification v0.1

Status: accepted on merge / normative City visualization specification  
Parent specification: `docs/product/stream-map-spec-v0.7.md`  
Evidence semantics: `docs/product/stream-map-city-confidence-contract-v0.1.md`  
Baseline main: `24cd444bfe564588b70c16a335f07d2c41627c0b`  
Date: 2026-09-05

## 1. Purpose

Define the next public Twitch City visualization from the City data that ViewLoom actually has.

This specification does not treat a City name as a creator coordinate. It defines City as an aggregate evidence-backed place grouping and keeps creator precision at Country / Region / City only.

Country choropleth behavior is not copied into City by default.

## 2. Existing City data contract

City mode is explicit:

```text
/api/twitch-stream-map?geography=city
/twitch/map/?geography=city
```

Default geography remains Country.

The existing City API already separates:

```text
mappedStreams          accepted Base City placement
countryOnlyStreams     accepted geography insufficient for City
baseCityConflicts      conflicting qualifying Base City evidence
cityCoverage           exact City-level reconciliation/accounting
identityContract       Twitch stable-ID coverage state
```

City identity coverage is explicit:

```text
stableTwitchUserIdState = unavailable | partial | available
loginIsStableIdentity   = false
```

Stable ID availability improves join integrity. It does not create geography.

## 3. Placement eligibility

### 3.1 Base City placement

Only accepted evidence with these claim kinds may place a stream in Base City:

```text
home_base
declared_location
```

### 3.2 Not Base City placement

These never place Base City on their own:

```text
current_location
temporary_location
birthplace
nationality
historical residence without current Base evidence
event venue
planned/future travel
context_only evidence
country-only evidence
```

Current/IRL remains a separate future layer.

### 3.3 Conflict behavior

Two or more accepted Base claims for different City places produce `base_city_conflict` and remain unplaced.

No newest-wins, source-rank, Country-centroid, nearest-City or name-similarity resolution is allowed without a separate accepted rule.

## 4. Privacy and precision boundary

Public City placement may expose:

```text
country
region when available
city
aggregate stream count
aggregate viewer count
accepted evidence provenance already allowed by the City contract
```

Public City placement must not expose or derive:

```text
street address
postal code
residential location
GPS
latitude/longitude belonging to the creator
building/venue coordinates as creator location
inferred travel path
```

If retained evidence contains precise-location keys prohibited by the City confidence contract, that record fails closed for public City placement.

## 5. Core visualization decision

### 5.1 Primary semantic object: City aggregate

The public visual object is a **City aggregate**, not a streamer point.

Canonical aggregate key:

```text
countryCode + region + city
```

where absent region is represented explicitly rather than guessed.

A City aggregate contains:

```text
city label
region label when available
country label
mapped stream count
mapped viewer count
stream rows belonging to that accepted City aggregate
evidence-source summary
```

### 5.2 No creator-point layer in v0.1

This specification does not authorize individual creator point markers.

A map symbol located at a City reference coordinate can easily be misread as the creator's exact location. Therefore v0.1 does not use creator-like pins as the primary City representation.

### 5.3 Geographic map representation

A geographic City map may render a City aggregate only from an **explicitly reviewed public reference geometry source** that represents the City/place itself rather than a creator location.

Allowed geometry forms, in preference order:

1. reviewed City/municipal administrative boundary polygon;
2. reviewed public City reference point used only as an aggregate City target when no usable boundary exists;
3. no map target, with the City remaining fully usable in the aggregate list.

A reference point, if later admitted, must be visibly styled and labeled as a **City aggregate/reference target**, not a creator pin.

No reference geometry may be generated by:

- Country centroid;
- arbitrary region centroid;
- browser geocoding guess with no retained source contract;
- streamer profile coordinate inference;
- IP/device/location telemetry;
- venue coordinate substitution.

### 5.4 Geometry fail-closed rule

City evidence and City reference geometry are separate concerns.

```text
accepted City evidence + no accepted City geometry
-> City remains in list/results
-> no invented map target
```

Geometry absence must never downgrade or discard valid City evidence from the non-map result.

## 6. Desktop composition

The desktop City view uses this information order:

```text
Geography / population / evidence controls
-> City coverage summary
-> City map/context surface
-> selected City aggregate when present
-> City aggregate list + mapped streams
-> City-specific unmapped/conflict diagnostics
```

The map is a geographic overview. The list is the exact-value and accessibility surface.

### 6.1 City map behavior

When accepted reference geometry exists:

- map and list select the same City aggregate state;
- selecting a City does not change evidence acceptance;
- selecting a City filters the mapped-stream drilldown to that aggregate;
- selection remains persistent until cleared or another City is selected;
- hover is informational only;
- selection and camera are separate state;
- no automatic deep zoom that implies street-level precision;
- explicit reset returns to the City overview camera.

When no accepted reference geometry exists for a City, list selection still works normally.

### 6.2 City aggregate list

The aggregate list is not optional fallback copy. It is a first-class product surface because it carries the exact City label and does not require coordinates.

Each row exposes at minimum:

```text
City · Region · Country
N streams
N viewers
```

Selection must be keyboard accessible and synchronized with any corresponding map geometry.

### 6.3 Selected City panel

A selected City panel exposes:

```text
City / Region / Country
mapped streams
mapped viewers
evidence-source summary
stable-ID coverage note for the relevant selected result when useful
Clear City
Show streams / focus stream list
```

It must not imply that the selected map geometry is the creator's live/current position.

## 7. Mobile composition

Mobile prioritizes exact City aggregates over map manipulation.

Order:

```text
compact Geography / Filters
-> City coverage summary
-> City aggregate list / selected City
-> compact map context
-> mapped streams
-> diagnostics
```

The City map may remain visible, but the user must not need precise tapping on small polygons/targets to use City mode.

Mobile requirements:

- City rows and selection controls meet tap-target requirements;
- selected City remains visible without requiring map hover;
- filters can collapse behind the existing compact control pattern;
- no horizontal overflow;
- map height remains bounded;
- list selection is the reliable path for small/overlapping City targets.

## 8. Metrics and visual encoding

City aggregate magnitude may be encoded by:

```text
Streams
Viewers
```

The control may reuse the Country metric labels, but City geometry semantics remain separate.

If a polygon/area fill is implemented, a bounded ordinal/log-scaled intensity treatment may be reused only for aggregate magnitude. It must not suggest location confidence.

Evidence confidence/consistency must never be encoded as viewer/stream intensity.

## 9. Evidence and identity display

Evidence provenance remains inspectable per mapped stream.

City UI must not collapse these concepts:

```text
accepted location evidence
City geometry source
Twitch identity/join status
```

They are independent.

Stable Twitch user ID state is displayed honestly:

- `available`: all parsed snapshot streams have stable Twitch IDs;
- `partial`: some have stable IDs and some do not;
- `unavailable`: no stable Twitch ID in the parsed snapshot;
- login remains a join key only.

No City placement is rejected solely because stable ID is unavailable when the current accepted API contract can still deterministically join that row by the existing bounded mechanism. Stable-ID gaps remain visible contract state rather than being fabricated away.

## 10. Diagnostics

City diagnostics must distinguish at least:

```text
country_only_at_city_resolution
base_city_conflict
other eligible-unmapped state from the parent API
excluded non-person
```

The UI must not merge `country_only_at_city_resolution` into a generic unknown bucket: it means accepted geography exists but does not reach City precision.

A Base City conflict must expose that the stream is intentionally unplaced; it must not silently choose one City.

## 11. URL and mode state

City mode remains explicit in URL state:

```text
?geography=city
```

Country remains the default when the parameter is absent.

A later City selection deep link may be added only if it can use a stable, unambiguous aggregate key. Display text alone is not sufficient if two City names collide.

Current/IRL remains disabled/separate and must not be activated by City selection.

## 12. Accessibility

Required:

- City aggregate list works without the map;
- selection state uses semantic buttons/pressed or selected state;
- keyboard focus is visible;
- map-only color is never the sole carrier of selected state or magnitude meaning;
- any intensity legend has text labels;
- map target has accessible City name when target geometry exists;
- conflict/country-only states are readable text, not icon-only;
- mobile controls remain usable at 390px viewport without horizontal overflow.

## 13. Browser verification matrix

City implementation must prove at least these scenarios:

1. accepted Base City with region;
2. accepted Base City without region;
3. multiple streams in the same City aggregate;
4. identical City name in different country/region keys remains distinct;
5. country-only accepted evidence stays unplaced at City resolution;
6. Base City conflict stays unplaced;
7. current/temporary City evidence does not enter Base City;
8. no creator coordinate/address leaks to public payload or DOM;
9. stable-ID state `available`;
10. stable-ID state `partial`;
11. stable-ID state `unavailable`;
12. accepted City with accepted boundary/reference geometry;
13. accepted City with no geometry remains usable in list;
14. desktop selection synchronization;
15. mobile list-first selection and no overflow;
16. Country mode remains unchanged when City code is present;
17. production structural smoke verifies both Country and City.

Browser assertions should target semantic structure and state, not transient prose fragments.

## 14. Implementation gates

Implementation is split so geometry cannot smuggle in new geography semantics.

### C1 — City aggregate model and selection

Build deterministic aggregate/group/selection core from the existing City API response.

No new geometry required.

Completion:

- aggregate keys deterministic;
- stream/viewer totals reconcile;
- conflicts/country-only excluded from mapped aggregate rows;
- list selection testable independently from MapLibre.

### C2 — City reference-geometry source audit

Before adding map targets, freeze the data source and matching rules for City reference geometry.

The audit must answer:

- source/license/update model;
- whether geometry is boundary or reference point;
- how `countryCode + region + city` resolves without fuzzy silent matching;
- collision/ambiguity handling;
- missing-geometry behavior;
- size/build/runtime cost;
- whether any network service or usage policy would be introduced.

No accepted source = no City map target. C1/list work may still proceed.

### C3 — City map aggregate renderer

Only after C2 acceptance:

- render accepted City aggregate geometry;
- synchronize map/list selection;
- use aggregate styling, not creator-pin styling;
- keep camera bounded away from street-level precision semantics;
- fail closed to list-only for unresolved geometry.

### C4 — City responsive/detail UI

Implement selected-City panel, stream drilldown, diagnostics, mobile ordering and accessibility.

### C5 — City production proof

Run deterministic contract/browser verification and current production structural smoke. Country must remain unchanged.

## 15. Explicit non-goals

v0.1 does not authorize:

- creator exact-location pins;
- live GPS/current-location City layer;
- City inference from Country;
- Country/region centroid creator placement;
- arbitrary geocoder results as accepted placement;
- automatic fuzzy City matching;
- Twitch/Kick aggregation;
- collector changes;
- collector cadence changes;
- D1 schema/binding changes;
- retention expansion;
- backfill;
- private/residential precision;
- inferred travel paths.

## 16. Product effect

With this specification, City becomes useful before precise map geometry exists:

- exact accepted City aggregates are selectable and countable;
- users can drill into streams by City without fake coordinates;
- Country-only and conflicts remain visible instead of being guessed away;
- map rendering can become richer only when a reviewed City geometry source exists;
- future Current/IRL work stays semantically separate.

The immediate implementation step after acceptance is **C1 City aggregate model and selection**, while **C2 City reference-geometry source audit** can proceed in parallel.
